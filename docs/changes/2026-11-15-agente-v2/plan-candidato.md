## Diseño (mínimo)
- **`src/catalogo.js`** (nuevo): `CATALOGO` (id, nombre, precio en centavos; archivo versionado, el cajero no edita precios) + `armarTicket(lineas)`: valida ids, enteros 1..20, suma en centavos, arma el concepto (≤100), rechaza total > `TOPE_CENTAVOS` (sin truncar). Única fuente del monto.
- **`src/agente.js`** (nuevo): `proponerLineas(texto, {fetchFn, key, modelo, presupuesto})` → llama a OpenRouter (`fetch`, sin dependencias) con system prompt fijo, texto del cajero como dato, catálogo solo `{id, nombre}`; pide JSON `{lineas:[{id,cantidad}], dudas:[]}`; validación local estricta: **cualquier** id ajeno, cantidad inválida o línea duplicada marca la propuesta como *incompleta* (no se descarta en silencio, con independencia de `dudas`); la UI bloquea «Cobrar» hasta corrección humana, también con el respaldo por reglas ( HTTP 200 con `error`/sin `choices` = fallo); `AbortSignal.timeout`, `max_tokens` acotado, texto de entrada ≤ 300 chars, sin reintentos. **Sin herramientas** (ni tool use): solo JSON → no existe superficie para «pagado/entregar».
- **Presupuesto:** tabla `uso_agente` en SQLite (persistente a reinicios): presupuesto en **centavos de MXN-equivalente/USD declarado** por día (`AGENTE_TOPE_DIA`): se fija un máximo conservador por llamada (modelo fijo + entrada ≤300 chars + `max_tokens` + tamaño máximo de respuesta en bytes), se **reserva persistentemente antes de salir a la red** y se deniega si no cabe; la reserva no se libera por timeout, fallo ni reinicio (consumo desconocido = consumido). Una llamada a la vez (mutex). Se registran moneda, periodo y el límite nativo configurado en la key antes de habilitar el agente. Presupuesto agotado → **503** (no 429: la UI toma 429 por PIN, `caja.html:151`). Además, límite de gasto en la propia key de OpenRouter (paso manual de Diego). Sin PIN válido: cero llamadas (la ruta queda tras el PIN existente).
- **Rutas** (`src/server.js`): `POST /api/agente` (PIN; devuelve líneas propuestas + total calculado con `armarTicket` + dudas; 503 si falta key/presupuesto → la UI cae al menú). `POST /api/ordenes` acepta `{lineas}` → `armarTicket` → `crearOrden` (reutiliza `core.js:66`); ignora monto/concepto del cliente cuando hay `lineas`. «Cobro manual» (concepto+monto libres) se conserva rotulado; el modo demo $0.01 pasa a variable del servidor (`MODO_DEMO`), no del cliente.
- **UI** (`public/caja.html`): el agente rellena el ticket (líneas editables: cantidades, no precios); «Cobrar» envía `lineas`; respuestas tardías no pisan un ticket editado (token de versión); rótulo «IA: OpenRouter · modelo» y aviso visible junto a la captura de que **OpenRouter recibe el texto**; edición de productos y cantidades invalida la confirmación y exige confirmar de nuevo; todo con `textContent`; si falla el agente, respaldo a `proponer` por reglas (corregir `pan: 1` en «tres piezas de pan») y menú manual; aviso de dudas/captura incompleta.
- **Secretos:** `OPENROUTER_API_KEY`, `AGENTE_MODELO`, `AGENTE_TOPE_DIA` en `.env.example` sin valores; barrido de secretos antes de cada push.
- **Datos a OpenRouter:** solo texto de captura + `{id,nombre}`; nunca PIN, webhook, CLABE ni pagos.
