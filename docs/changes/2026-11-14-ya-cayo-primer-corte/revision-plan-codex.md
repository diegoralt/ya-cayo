## Bloqueantes

- P1 — **Una conciliación atrasada puede reabrir una orden entregada.** Escenario: webhook y polling consultan simultáneamente; el primero marca pagada, el cajero entrega y el segundo vuelve a escribir pagada. El `UPDATE` condicional protege la transición de entrega, pero el plan no condiciona la escritura de `reconcile` ni exige una transacción que abarque transición, registro de entrega y deduplicación (`plan-candidato.md:8`–`10`). `entregas(orden_id UNIQUE)` evita dos filas; por sí solo no evita reactivar el botón ni un estado inconsistente si el segundo `UPDATE` se confirma y el `INSERT` falla. Tampoco queda claro si «la misma función» implica que webhook/polling ejecutan la entrega sin acción humana (`plan-candidato.md:10`, `plan-candidato.md:21`). **Arreglo:** fijar transiciones monotónicas: conciliar nunca degrada/reabre entregada; registrar transacciones y excepciones sin sobrescribirla. Después del GET, releer estado dentro de una transacción SQLite corta; entrega = `UPDATE` condicionado con comprobación de filas afectadas + `INSERT`, ambos con commit/rollback conjunto. Webhook/polling solo concilian; el botón solicita la transición de entrega compartida. Validar intercalación explícita «GET A → GET B → confirmar A → entregar → aplicar B», dos transactionId distintos y fallo entre UPDATE/INSERT: estado entregada, una fila y una sola entrega aceptada, también tras reiniciar. Cierra el requisito de `revision-codex.md:14` y `sintesis.md:11`; los nombres de tests de H2 no fijan todavía esa invariante (`plan-candidato.md:19`).

- P1 — **El respaldo deja una ventana sin recuperación al vencer el QR.** Escenario: pago efectivo un instante antes del vencimiento, webhook perdido y GET anterior todavía sin pago; al vencer, la orden deja de estar «viva» y cesa el polling (`plan-candidato.md:8`). Aunque `datePaid` permitiría aceptar ese pago (`plan-candidato.md:9`), nunca se vuelve a consultar. Además, no hay observación posterior que descubra tardíos/segundos pagos una vez cerrada la orden (`plan-candidato.md:11`). **Arreglo:** definir qué estados se siguen conciliando, reintento tras errores y una ventana acotada posterior al vencimiento/entrega, con reconciliación manual disponible después; fijar plazo objetivo de recuperación y cómo se informa una consulta fallida. Mantener separado el vencimiento del QR del cierre de conciliación. Validar webhook ausente + pago anterior al vencimiento que aparece después; pago posterior → tardío sin entrega; respuesta PENDING/error → ninguna habilitación; segundo pago descubierto después de entregar → excepción con contador uno. El endpoint correcto sí queda cerrado (`plan-candidato.md:8`; [referencia oficial](https://docs.pey.mx/docs/api/get-co-di-qr-transactions/)); la recuperación exigida en `revision-codex.md:16` y la política de `revision-codex.md:22` solo están parcialmente cubiertas por H3 (`plan-candidato.md:20`).
